# baseline.txt — (taxonomy node :: pack file) pairs where the node's prose does
# not describe the threat that pack rule detects.
#
# Read by cmd/check-pack-taxonomy-fit. See that package's doc comment for what
# the check measures and where it deliberately diverges from the comply-side
# gate. A line here is a known flag; any pair NOT listed is new and fails CI.
#
# Format: <taxonomy node id> :: <pack file basename>. Comments after '#'.
#
# Keyed on the PAIR, not the node, so a node that is already known-bad cannot
# silently accrete more mismatched rules.
#
# BURN IT DOWN. Two ways to clear a line, both improving the attestation text a
# customer reads:
#   1. Point the rule at a node whose prose describes what it detects.
#   2. Broaden the node's prose so it covers the family it has accreted.
# Adding a NEW line requires Gary + Kai sign-off. Removing one is MANDATORY
# once the pair stops misfitting — the checker reports STALE entries and fails.
#
# Bootstrap:  go run ./cmd/check-pack-taxonomy-fit -taxonomy <dir> -write-baseline
# NOTE: -write-baseline DISCARDS the hand-written verdicts below. It is a
# bootstrap tool, not a maintenance one — to clear an entry, delete its line.

# CI/CD Pipeline Configuration Injection — CLEARED 2026-08-13 (#3335).
#   THE ONLY SEED ENTRY. This file is now empty of pairs.
#
#   Verdict was REAL, baselined rather than guessed at because the remedy was a
#   judgement call. The nine rules were two families and took two answers, and
#   in both cases the destination node had ALREADY declared ownership in prose —
#   the rules simply never moved. Worth remembering: the fix for a misfit is
#   more often a node that already exists than a node that needs writing.
#
#   - Azure DevOps logging commands (ado-prependpath, ado-setvariable,
#     ado-uploadfile) -> github-actions-env-injection, broadened to the
#     mechanism (comply#3657). They ARE pipeline injection but not the KIND the
#     old node described: it says an agent "writes to CI/CD pipeline
#     configuration files", and an ADO logging command writes no file — it is
#     emitted on stdout and interpreted by the running agent. The GitHub node
#     already covered the identical channel: prependpath IS $GITHUB_PATH,
#     setvariable IS $GITHUB_ENV, and GitHub shipped the env-file form only
#     because it disabled its own stdout form in CVE-2020-15228. One mechanism,
#     two vendors — not two threats.
#   - Dockerfile / docker-compose / devcontainer writes -> build-script-injection.
#     Its abstract already enumerated "Dockerfile RUN layers" and "dev container
#     lifecycle hooks (devcontainer.json)", and already stated the boundary
#     these rules sat on the wrong side of: "without touching CI/CD pipeline
#     configuration files that have dedicated security monitoring". Compose was
#     the only open call and was added explicitly (comply#3657), split into the
#     executing keys (command/entrypoint/build — this node) and the isolation
#     keys (privileged/security_opt/host binds — cross-referenced to
#     container-escape).
#
#   The MCP twin `mcp-sc-block-dockerfile-write` moved with group 2. It had read
#   as a FIT purely because it shares the word "filesystem" (an MCP tool name)
#   with the node's prose — the coincidence-rescue the majority-zero rule exists
#   to prevent, surviving only because sibling rules in that file matched
#   honestly. If a pair in this file ever clears, check its MCP twin by hand;
#   the score will not flag it.
#
#   The "also in" hint on this pair (agent-orchestration-hijacking, sharing
#   echo/json/printf/python/sed) was noise — shell verbs from the command
#   regexes, and it pointed at neither correct destination. Read "also in" as
#   evidence the terms are real taxonomy vocabulary, never as a routing
#   recommendation.
